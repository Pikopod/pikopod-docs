title: Replay gate
description: Gate builds offline on recorded traffic against frozen baselines.
---

```bash
pikopod agent replay --ci
pikopod agent replay --ci examplepay --handoff replay.json
```

```text
examplepay: 37 recordings gated (0 pre-warmup skipped) — 0 finding(s) at or above medium, 0 accepted
clean — no drift against frozen baselines
```

`agent replay --ci` reads each recorded response from `<data_dir>/recordings/<upstream>.ndjson` and diffs it against its frozen baseline family, entirely offline. No network, no provider account, no running agent.

## What it compares

Each JSON recording is matched to its `(method, template, status class)` family and diffed the same way live traffic is: fields added or removed, types changed, values outside the known set, a field arriving null, a status code moving within its class. Findings are deduplicated per method, template, kind, field and detail, and each carries the fingerprint `pikopod agent accept` takes.

## Risk tiers

A provider adding a field should not block a release. A type flip on `amount` must. Every finding is graded by what breaks consumers, and `--fail-on` sets the lowest tier that fails the build:

| Risk | Kinds |
|---|---|
| `high` | `field_removed`, `type_changed`, `field_nullable`, `status_new`, `status_code_changed`, `error_shape_changed` |
| `medium` | `enum_value_new` |
| `low` | `field_added` |

A finding the provider's new spec version documents drops one tier. The default is `medium`, so additive fields are accepted and everything else fails. Findings below the threshold are printed under `accepted` and never fail the gate:

```text
examplepay: 37 recordings gated (0 pre-warmup skipped) — 1 finding(s) at or above medium, 1 accepted
  DRIFT high   type_changed         GET /charges/ch_{id}  amount string  fp_5f4025d6b870
accepted (below --fail-on medium):
  DRIFT low    field_added          GET /charges/ch_{id}  fee_bearer string  fp_b9d1b2e5950b

drift found — failing the gate (exit 1)
```

`--fail-on low` fails on everything, `--fail-on high` only on removals, retypes and status changes:

```text
examplepay: 37 recordings gated (0 pre-warmup skipped) — 2 finding(s) at or above low, 0 accepted
  DRIFT high   type_changed         GET /charges/ch_{id}  amount string  fp_5f4025d6b870
  DRIFT low    field_added          GET /charges/ch_{id}  fee_bearer string  fp_b9d1b2e5950b

drift found — failing the gate (exit 1)
```

A drift accepted with `pikopod agent accept <fingerprint>` is honoured here too: it is listed in its own `accepted` block, whatever its tier, and does not fail the gate. See [ack, accept, baseline](/reference/cli/ack-accept-baseline).

## What it skips

- Recordings whose family is not frozen yet. They are counted as pre-warmup skipped.
- Non-JSON recordings.
- New values on fields listed in `volatile_fields`. Presence, type and nullability of those fields are still checked.

## Exit codes

| Exit | When |
|---|---|
| `0` | Every gated recording matched, or every finding was below `--fail-on` or accepted. |
| `1` | Drift at or above `--fail-on` found. |
| `2` | No baselines or no recordings for an upstream, or an unknown `--fail-on` tier, which is a tool problem, never conflated with drift. |

## In CI

The gate needs the `data_dir` the agent wrote, or a copy of it. Ship the `baselines/` and `recordings/` directories as an artifact, or mount the volume read-only:

```bash
./pikopod agent replay --ci --handoff replay.json
./pikopod pr comment --handoff replay.json
```

The handoff is `{"source":"replay-ci","records":n,"fail_on":"medium","findings":[…],"accepted":[…]}`; each finding carries `risk` and `fingerprint`, each accepted entry also `because`. `pr comment` renders the findings. See [CI integration](/gate/ci-integration).

## Recordings as scenarios

For a regression suite that does not need the agent's data at all, turn a traffic window into an ordinary scenario pack and commit it:

```bash
pikopod scenario from-recordings examplepay --last 20 --name checkout-flow
```

See [Generated packs](/scenarios/generated-packs).
