title: Modes
description: Put the served sandbox into a scenario's standing state, then run your own tests against it.
---

`pikopod scenario check` drives its own requests against a throwaway engine, so your application is never in the loop. A mode is the other half: it arms the scenario's standing conditions on the sandbox `pikopod up` is serving, and then your own tests, your own app, Postman, or plain curl meet the failure.

```bash
pikopod mode set examplepay timeouts
```

```text
mode: timeouts (from archetype or pack timeouts)
  armed   latency on GET /charges
point your app at the sandbox and run your own tests; clear it with `pikopod mode clear examplepay`
```

Now run your integration's test suite against `http://127.0.0.1:4600/examplepay`. Every `GET /charges` is delayed, and your timeout handling is what gets exercised.

## What a mode arms

The scenario's standing conditions: the faults it injects and the state it seeds. Its request steps are not run; those are yours to make. A scenario whose first step is a request has no standing state and is refused with the reason.

```bash
pikopod mode set examplepay rate_limit_backoff
pikopod mode set examplepay declines --bind op=createCharge
pikopod mode set examplepay incident-14835fa32dfb
```

Packs work as well as archetypes, so a reproduced production incident can be the standing state your whole suite runs against.

## Global, and standing

A mode is global to the sandbox and stays until cleared. Two test suites running against one sandbox see each other's faults, and a fault with a `times` window counts down across both. Run one suite at a time against a given sandbox, or give each its own `pikopod up` on a different port.

```bash
pikopod mode show examplepay
pikopod mode clear examplepay
```

`clear` leaves the standing state and clears every fault on the sandbox.

## Verify what your tests sent

A mode arms the failure. `verify` asks whether your client did what the scenario expects once it met that failure. It reads the sandbox's request journal and judges it against the scenario's verification steps: request order and spacing, webhook counts, stored state. It never arms, seeds, or resets anything.

```bash
pikopod mode set examplepay retry_storm
```

```text
mode: retry_storm (from archetype or pack retry_storm)
  armed   error 503 on POST /charges (first 2 per idempotency-key)
  verify  1 step(s) with `pikopod mode verify` after your tests run
point your app at the sandbox and run your own tests; clear it with `pikopod mode clear examplepay`
```

Run your tests. `retry_storm` refuses the first two creates under one idempotency key with `503` and answers the third, so a client that retries correctly sends three. Then:

```bash
pikopod mode verify examplepay
```

```text
✓ retry_storm — PASSED (3 matcher(s) matched in order)
    PASSED         storm-shape      3 matcher(s) matched in order
```

A client that gave up after the second `503` fails, and the summary says which expectation the journal never met:

```text
✗ retry_storm — FAILED (matcher 2 (POST /charges) never matched; scanned 2 of 2 journaled request(s))
    FAILED         storm-shape      matcher 2 (POST /charges) never matched; scanned 2 of 2 journaled request(s)

your client did not do what the scenario expects — exit 1
```

Exit `0` when every step passed, `1` when the client fell short, `2` when no mode is set or the mode's scenario has no verification step. Spacing between requests is judged on wall-clock time, because your client made them in real time. Clear the mode between suites, or the next suite is judged against the last one's requests too.

## From a test

The Go package `pkg/sandboxtest` does the same inside a test, with no `pikopod up`: `New`, `Mode`, run your code, `Verify`. See [Use it from a test](/scenarios/from-a-test).

## From a coding agent

The same operations are MCP tools: `set_mode`, `mode_verify`, `clear_mode`, and `get_requests` to read the journal itself. See [MCP tools](/reference/mcp-tools).

## When you want one fault, not a story

```bash
pikopod chaos examplepay --kind error --status 503 --method POST --path /charges
```

See [Faults](/sandbox/faults).

## When the failure depends on the request

A mode and a fault answer every matching request the same way. For "answer 422 when this reference already exists", write a [rule](/sandbox/rules).
